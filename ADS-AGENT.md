# ИИ-агенты рекламы Wildberries и Ozon

`ads-agent.mjs` дважды в день (06:17 и 15:17 мск, workflow «ИИ-агенты рекламы WB и Ozon») просматривает рекламу WB и Ozon. По каждой кампании он решает: оставить, снизить или поднять ставку, поставить на паузу. Кроме того, он разбирает поисковые запросы всех активных кампаний и исключает те, что не окупаются; переносит исключения между кампаниями одного товара; готовит план с вариантами запуска, которые владелец одобряет в Telegram; и проверяет, к чему привели его прошлые решения.

Сводка по обоим агентам — на главной («Обзор» → «ИИ-агенты рекламы»). Все решения с причинами — во вкладке «Реклама». Сырые данные — в `ads-agent.json`, память агента — в `ads-memory.json`.

| Файл | Что внутри |
|---|---|
| `ads-agent.mjs` | общий цикл, правила, жёсткие ограничения, адаптер WB |
| `ozon-ads.mjs` | адаптер Ozon Performance API («Оплата за клик») |
| `ads-brain.mjs` | память, проверка результатов, самонастройка, команда Claude |
| `ads-queries.mjs` | оценка запросов, база знаний по запросам каждого товара, перенос исключений |
| `ads-plan.mjs` | план развития кабинета, варианты запуска, ответы из Telegram |
| `ads-agent.config.json` | лимиты и режимы, которые задаёт владелец |

## Как он считает

- **Маржа до рекламы** — прибыль товаров кампании без учёта рекламы, делённая на выручку, за 30 дней (Торгстат, `data.json`). Это потолок: выше него каждый рекламный заказ в минус.
- **ДРР** — расход на рекламу, делённый на выручку с рекламных заказов с поправкой на процент выкупа. Считается за 30, 14 и 7 дней.
- **Цель** — `targetShare` от маржи (по умолчанию 60%), но не больше `maxDrr` (25%).

| Ситуация | Действие |
|---|---|
| ДРР выше цели | ставка вниз, не больше `bid.maxStepPct` за раз |
| ДРР ниже 70% цели, есть заказы и остаток | ставка вверх на `bid.upStepPct` |
| ДРР выше маржи × `stop.overMarginFactor` и за 30, и за 14 дней | пауза |
| Товар убыточен ещё до рекламы | пауза |
| Потрачено больше `stop.noOrdersSpend`, заказов нет | пауза |

**Кампании WB не закрываются, а ставятся на паузу.** Закрытие в WB необратимо и уничтожает работу, накопленную в кампании: собранные поисковые кластеры и минус-фразы, выставленные вручную. Если после чистки запросов кампания на паузе окупилась бы, агент сам исключает плохие запросы и перезапускает её (`plan.auto`), а следующие `stop.restartGraceDays` дней не ставит её снова на паузу, пока копится новая статистика. Так же сам он запускает новую кампанию вместо закрытой, если расчёт показывает прибыль (в пределах `launch.maxTotal`).

**Закрыть кампанию навсегда агент может только с разрешения владельца.** Если кампания стоит на паузе из-за убытка дольше `stop.askAfterDays` (5) дней и перезапуск не окупится, агент сразу пишет в Telegram: «🔒 Нужно ваше решение: закрыть кампании?» со списком под номерами. Ответ «закрыть 1 2» или «закрыть все» — закроет при следующей проверке и подтвердит; «оставить 1» — оставит на паузе и месяц не спросит. Минус-фразы закрываемой кампании к этому моменту уже лежат в базе агента и переносятся в другие кампании товара. Открытые вопросы видны в вечернем плане и на главной странице дашборда. Кампанию, закрытую по ответу владельца, агент сам заново не создаёт.
| Товара нет на складе | пауза; агент сам включит, когда товар вернётся |
| Мало данных (`minSpend`, `minClicks`) | ждать |

## Поисковые запросы (WB)

Агент разбирает кластеры запросов по всем активным кампаниям (до `queries.maxCampaigns`, самые затратные первыми) и сравнивает каждый запрос с показателями самого товара в этой кампании: его конверсией в заказ, средней ценой клика и прибылью с одной продажи.

Запрос исключается (в минус-фразы), когда:

| Правило | Пример |
|---|---|
| нет заказов там, где при обычной конверсии товара их было бы уже `queries.minExpected` и больше, а потрачено больше прибыли с продажи | 60 кликов при конверсии 5% — ждали 3 заказа, а их 0 |
| заказ с запроса стоит дороже прибыли с него в `queries.costFactor` раза | 400 ₽ за заказ при прибыли 150 ₽ |
| конверсия ниже `queries.lowCrShare` от средней по товару, и заказ дороже прибыли | 1% против 5% |
| клик дороже среднего в `queries.cpcFactor` раза, и заказ дороже прибыли | 12,5 ₽ против 6 ₽ |

Если в запросе есть слово из названия или категории товара, он часто приносит карточке основной трафик. Такие запросы агент сам исключает только при сильных цифрах: когда при обычной конверсии ждали `queries.relatedStrongExpected` заказов, а не было ни одного. В остальных случаях их разбирает помощник-ИИ, а без Claude они не трогаются. Помощник может исключить только запросы, которые по цифрам не окупаются.

Запросы, которые продают с заказом дешевле `queries.goodShare` от прибыли, агент запоминает как хорошие. В кампаниях с ручной ставкой и оплатой за показы он поднимает ставку на такие кластеры на `bid.upStepPct` (не чаще раза в неделю).

### База знаний и перенос

Для каждого товара агент хранит в `ads-memory.json` все исключённые запросы — свои и сделанные сотрудниками в кабинете — и запросы, которые продают. Исключения переносятся:

- во все остальные активные кампании этого товара;
- в каждую новую кампанию, которую агент создаёт (вариант плана или автозапуск).

Добавить в кампанию нужный запрос через API WB нельзя: кластеры WB формирует сам. Поэтому переносятся исключения — именно они направляют показы на хорошие запросы. Плюс ставки на продающие кластеры там, где WB это разрешает.

Кампании, которые агент закрыл раньше (до перехода на паузы), он один раз прочитал: их минус-фразы сохранены в базе и переносятся в живые и новые кампании тех же товаров.

## План и варианты запуска

Каждый запуск агент составляет план (`plan` в `ads-agent.json`, вкладка «Реклама» → «План по кабинету»):

- **что сделано за сутки** — паузы, ставки, исключённые и перенесённые запросы, экономия в день;
- **что дальше** — что агент собирается сделать в ближайшие дни (с Claude — его собственные шаги);
- **варианты запуска** (до `plan.maxVariants`) — только те, где расчёт обещает прибыль:
  - **перезапуск** кампании на паузе: сколько стоили плохие запросы, каким был бы ДРР без них, нужно ли снизить ставку;
  - **новая РК вместо закрытой** — для товаров, чьи кампании были закрыты: с переносом всех их минус-фраз;
  - **новая РК** для прибыльного товара без рекламы — с расчётом прибыли на 1000 ₽ рекламы.

Вечерний отчёт в Telegram (21:00) приходит двумя сообщениями: итоги дня и план. Чтобы запустить варианты, ответьте боту: **запуск 1 3** (номера) или **запуск все**. При следующей проверке (06:17 или 15:17) агент выполнит их — не больше `plan.maxPerRun` за раз, с бюджетом `plan.budget` ₽ каждый — и ответит в чат, что сделано. В режиме проверки (`dry-run`) варианты только отмечаются, кабинет не меняется.

## Выбор товаров для запуска

Кандидат — прибыльный товар без рекламы: маржа до рекламы от `launch.minMargin`, остаток от `minStock` шт. и не меньше чем на `minStockDays` дней продаж, продажи от `minSales30`, рейтинг от `minRating`, без себестоимости — нет.

Затем идёт расчёт отдачи. Агент берёт среднюю цену клика в этом кабинете, конверсию карточки из воронки (с поправкой 0,7 на рекламный трафик), выкуп и прибыль с продажи. Товар запускается, только если отдача на рубль клика выше цены клика в `launch.minHeadroom` раза. Кандидаты сортируются по ожидаемой прибыли на 1000 ₽ рекламы. Всего агент запускает не больше `maxTotal` кампаний и не перезапускает товар, кампанию которого уже закрыл.

## Ozon

Работает с кампаниями «Оплата за клик» через Performance API:

- **Средняя стоимость клика** (`TARGET_BIDS`) — агент меняет ставку за клик, не выше `ozon.maxCpcRub`.
- **Целевой расход** (`TARGET_CIR`) — агент двигает целевой ДРР, который держит сам Ozon, не выше цели продавца.
- **Остальные автостратегии** — ставку ведёт Ozon, агент только включает и выключает кампанию.
- **Товары, тянущие кампанию в минус** (расход без заказов или убыток до рекламы), агент убирает из кампании, если в ней есть другие товары.
- **Закрыть насовсем** в Ozon нельзя: «закрыть» означает выключить, это обратимо.

У Ozon свой выключатель `ozon.mode`. Пока он `dry-run`, агент Ozon только пишет план, даже если WB работает в боевом режиме. Ответы Ozon по статистике (`/statistics/daily/json`, `/statistics/products/sku`) в документации не описаны полностью. Поэтому при первом запуске агент пишет в лог образец каждого ответа. Перед `ozon.mode: "live"` стоит посмотреть первый план.

Ключи: seller.ozon.ru → Настройки → API-ключи → Performance API → создать сервисный аккаунт и ключ. Секреты GitHub:

- `OZON_PERF_SAKOVSKY_CLIENT_ID`, `OZON_PERF_SAKOVSKY_CLIENT_SECRET` — «Озон Саковский»;
- `OZON_PERF_SUAVISS_CLIENT_ID`, `OZON_PERF_SUAVISS_CLIENT_SECRET` — «Suaviss Озон».

## Как агент учится

1. **Проверяет свои решения.** Через неделю после каждого действия (после запуска — через две) агент сравнивает прибыль кампании в день до и после и ставит оценку: помогло, ничего не изменило, навредило. Итоги копятся в `ads-memory.json`.
2. **Сам настраивает пороги.** Если большинство последних снижений ставки навредило, шаг снижения уменьшается; если помогло — растёт. С Claude агент может по итогам проверок сдвинуть и другие пороги из списка `TUNE_BOUNDS` в `ads-brain.mjs`. У каждого есть жёсткие границы, за один запуск значение меняется не больше чем на четверть.
3. **Ведёт уроки.** Claude после каждого запуска переписывает список уроков (до 12): оставляет подтверждённые, убирает опровергнутые, добавляет новые. На следующем запуске он читает их вместе с итогами проверок.
4. **Собирает команду помощников.** Ведущий агент Claude сначала решает, кого отправить на детальный разбор: чистить запросы, проверять товары для запуска, разбирать, почему просела кампания, проверять свои прошлые решения. Каждому помощнику он пишет задание и даёт нужный срез данных. Помощники работают параллельно (до `llm.maxHelpers`), ведущий читает их отчёты и принимает решения. Состав команды на следующий раз он сохраняет в памяти.

Чего агент не может менять сам: свой код, режимы `mode` / `ozon.mode`, денежные лимиты (`budget`, `launch.budget`, `maxTotal`, `stop.maxPerRun`, потолки ставок) и список `protect`. Это решает владелец.

Без `ANTHROPIC_API_KEY` работают правила из таблицы, чистка запросов по цифрам, расчёт запусков, проверка результатов и самонастройка шага ставки. Уроки и помощники требуют Claude.

## Ограничения, которые проходит любое решение

- поставить на паузу из-за убытка можно только кампанию, убыточность которой подтверждена цифрами;
- шаг ставки, её пол и потолок ограничены;
- ставку одной кампании не меняют чаще раза в `bid.cooldownHours`;
- за запуск закрывается не больше `stop.maxPerRun` кампаний;
- кампании из `protect` агент не трогает.

Закрытие кампании в WB необратимо, поэтому агент WB ничего не закрывает (пока `stop.hardClose` = `false`).

## Включение

1. Токены WB (`WB_SAKOVSKY_TOKEN`, `WB_DARMIL_TOKEN`) должны иметь категорию «Продвижение» **с правом записи**. Токен только на чтение даст план, но не изменения.
2. Для решений команды Claude — секрет `ANTHROPIC_API_KEY`.
3. Для Ozon — четыре секрета выше; затем, после проверки плана, `"ozon": { "mode": "live" }`.
4. Разовый запуск: Actions → «ИИ-агенты рекламы WB и Ozon» → Run workflow.

`budget.autoTopUp` (пополнение окупающихся кампаний WB) и `ozon.launch.enabled` (новые кампании Ozon) выключены: они тратят деньги и включаются отдельно.

Проверка логики: `node ads-agent.test.mjs`.

## Отчёт в Telegram

Каждый вечер в 21:00 мск workflow «Отчёт агента рекламы в Telegram» присылает картинку: что агент закрыл, запустил, где менял ставки, какие запросы убрал, плюс скриншот блока агента с дашборда.

1. В Telegram откройте @BotFather → /newbot, придумайте имя. Он пришлёт токен.
2. GitHub → Settings → Secrets and variables → Actions → New repository secret: `TELEGRAM_BOT_TOKEN` = токен.
3. Откройте своего бота и нажмите «Старт».
4. Actions → «Отчёт агента рекламы в Telegram» → Run workflow. Первый отчёт придёт в чат, бот пришлёт номер чата: добавьте его секретом `TELEGRAM_CHAT_ID`.

Проверить вид отчёта без отправки: `node ads-report.mjs --html` → `ads-report.html`.
